## 〇、台账使用规则

1. **只追加，不改写。** 新批次在 §二 表格末尾追加一行、在 §三 末尾追加一节即可。已写下的批次描述、commit、验证数字**不得回改**——历史记录的价值在于它不可被追溯修改。
2. **发现旧条目写错时，不改正文，追加勘误。** 在 §三 末尾的「勘误记录」小节登记「日期 / 原条目 / 错在哪 / 代码依据」。
3. **每个批次必须有 commit 号。** 没有 commit 的工作不进台账（未提交等于未交付）。
4. **禁止填写估算与预测。** 台账只写已发生的；工期、预计行数、预期效果一律不写。
5. **验证数字必须是当次真实输出。** 若当时未归档，写「当次未归档」并给出当前基线，**不得倒填数字**。
6. **本文不含本机绝对路径**，路径一律相对仓库根。

### 批次 ②-A 交互缺陷修复（空转 · 手牌重叠 · 释义浮层）

**起止 commit 与日期**：`b67d6aa`（2026-09-14）→ `ca79737`（2026-09-14）

**对外变化**

- 手牌可逐张选中，融合（同属性两张合一）恢复可用。

### 批次 ②-B 引擎大修 + 四层守卫 + 归墟弃牌

**起止 commit 与日期**：`31f6699`（2026-09-15），单提交 16 个代码文件、+3309 / −348 行

**目标与背景**

批次 ②-A 之后暴露出 3 个 P0 + 6 个 P1 引擎缺陷，根因是「数值散落在多个文件、契约只在人脑里」。当时缺的不是补丁，而是**让错误无法被提交进来的防线**。

**实现要点**

- **L1 类型层**：`STATUS_BEHAVIOR: Record<StatusId, …>` 强制每个状态都有行为定义；`EnemyIntent` 用判别联合；`EFFECT_HANDLERS` 穷尽表配 `assertNever`；`Equipment.qiCapSide` 改为必填。
- **L2 数据层**：所有数据表用 `satisfies readonly X[]`，数据写错时 `tsc` 直接报错而不是运行期静默。
- **L3 契约层**：`src/game/engine/contract.test.ts` 33 条断言（A1–A7），把「必须永远为真」的引擎不变量写成测试。
- **L4 构建层**：`scripts/架构守卫.mjs`（555 行、8 项检查）——禁随机源、节气读取归属、hex 越界、死 keyframe、零引用常量、状态完备性、节气实装状态、常量关系。
- **归墟弃牌**：`HAND_LIMIT = 6`、`HAND_DRAW_CAP = 10`（必须大于上限，否则永远不触发）、`phase = 'relic'`；超限时进入归墟阶段，弃哪几张由玩家权衡，弃置的牌按 `relicQiOf()` 化为对侧炁，且敌方会「吞食」弃牌获得护盾。
- **铁律落地**：`addBase` 只有装备可用（`assertNoIllegalAddBase`）；节气必须 Hook 化，`engine/hooks.ts` 是全引擎唯一读 `solarTermId` 的地方。
- 补三册素材提示词（`素材提示词.md` / `卡面与界面提示词.md` / `界面提示词.md`）。

**对外变化**

- 手牌超过 6 张时不再被静默截断，而是进入「归墟」——玩家主动选择弃哪几张，并把它们化成另一脉的炁。
- 节气、十神、架势的数值开始有可解释的来源，界面释义层与引擎一致。

**验证结果**

- `contract.test.ts` 33 条全绿；`guard` 8 项检查 0 error。
- 守卫首次运行即暴露出全部既有债务（hex 豁免、死 keyframe、零引用常量、中文台账），这些债务此后一直以 ⚠ 形式被追踪，未再增长成 error。

### 批次 ③ i18n 骨架（S0 + S1 + S5）

**起止 commit 与日期**：`6f7fcd8`（2026-09-16），23 个代码文件、+637 / −88 行

**实现要点**

- **S5 存档平滑迁移**：旧实现「版本不符 → 回退默认档」会抹掉通关记录与装备，改为 `migrateSave()` 纯函数逐字段合并并补 `locale`。
- 三批完成：S0 骨架、S1 数据层枚举（五行 / 类别 / 状态）、S5 存档。

**对外变化**

- 玩家不可见（`locale` 目前只有 zh-CN）。但界面文案从此有了唯一归属，后续新界面可以只加键不改逻辑。
- 存档版本升级不再清空进度。

**验证结果**

- `src/i18n/i18n.test.ts` 10 条：键完备性 + 孤儿键扫描 + 插值参数。
- `guard` §9 中文台账开始出现「（待迁移）」分级，S2 / S3 / S4 被显式标注为未完成。

## 三、里程碑候选区间（供未来认证使用）

### 3.1 判定口径

认证需要「一个可对外观测的阶段 ≳ 10 个代码文件 / > 2000 行变动」。为此对每个候选区间做了实测统计：

- **代码文件数** = 区间内变动的 `*.ts` / `*.tsx` / `*.mjs` 文件数（**不含** png、md、json、css）。
- **代码行变动** = 同一批文件的 `新增 + 删除` 行数（含注释；不含二进制）。
- 数据来源：`git diff --numstat <区间> -- '*.ts' '*.tsx' '*.mjs'`。

1. **剔除初始化提交后，严格同时满足两条门槛的区间有 4 个**：②-A（`b67d6aa`→`ca79737`，2948 行 / 10 文件）、②-B（`31f6699`，3657 行 / 16 文件）、`bd53593`+`18cd304`（6300 行 / 30 文件，或其中任一单提交也满足）、以及批次 ① 整体（但含初始化水分）。
2. **原先「很可能仍不满足 2000 行」的担忧只对了一半。** `31f6699`、`bd53593`、`18cd304` 三个提交的行数都**大幅超过** 2000 行；真正不满足的是另外两个：`fbc81e5` 行数够（2383）但代码文件只有 9 个，`6f7fcd8` / `1c4a77f` 文件数够（23 / 22）但行数只有 725 / 1155。
3. **体量与价值不是一回事。** `1c4a77f` 只有 1155 行，却交付了择道面板与特效层取色治理；`4e7d1be` 0 行代码却让界面从 CSS 底变成素材态。认证若只看行数，会系统性低估「接入类」与「素材类」工作——这一点必须在认证材料里显式说明，**不要靠改数字去凑**。
4. **最扎实的对外可观测阶段是批次 ⑤**（战斗屏 2147 → 259 行 + 29 张素材接入，6300 行变动 / 30 文件），它同时满足「体量」「结构改善」「玩家可见」三项，且回归证据（三相截图）是留档的。
